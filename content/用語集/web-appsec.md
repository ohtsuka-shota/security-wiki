## セキュアコーディング
開発段階から脆弱性を生み出さないように配慮したコードの書き方・設計方針。リリース後に脆弱性診断で問題を発見して修正するよりも、設計・実装の段階からインジェクション対策や認証・認可の仕組みを正しく組み込んでおく方が、修正コストも手戻りも小さく済むという考え方(シフトレフト)に基づいている。言語やフレームワークごとにセキュアコーディングのガイドラインが公開されており、チームでのコードレビューやlintツールによる自動チェックと組み合わせて運用されることが多い。

## 入力値検証(バリデーション)
外部から受け取るデータが想定した形式・範囲であるかを確認する処理。メールアドレスの形式になっているか、数値の範囲が妥当か、文字列の長さが制限内かといった基本的なチェックを行うことで、想定外のデータによる処理の異常動作を防ぐ、インジェクション系攻撃対策の最も基本的な土台になる。ただし入力値検証だけでは完全な対策にならない場合も多く、後述のプリペアドステートメントやエスケープ処理と組み合わせて多層的に防御する「深層防御」の考え方が重要になる。

## プレースホルダ / プリペアドステートメント
SQL文の雛形(プレースホルダ)にパラメータを後からデータとして安全にバインドする仕組み。あらかじめ`SELECT * FROM users WHERE id = ?`のような形でSQL文の構造を確定させておき、ユーザーからの入力値はあくまで「値」としてデータベースエンジンに渡されるため、入力値がどのような文字列であってもSQL文の構造自体を書き換えることができなくなる。SQLインジェクションの最も効果的で基本的な対策とされ、多くのプログラミング言語のデータベースライブラリで標準的に提供されている。

## エスケープ処理
HTML・SQL・シェルコマンドなどで特別な意味を持つ文字(`<``>``'``;`など)を、無害な文字列(`&lt;`など)に変換する処理。これらの文字がそのまま出力・実行されると、意図しないタグの挿入やコマンドの区切りとして解釈されてしまうため、文脈ごとに危険な文字を無害化することでXSSやインジェクション系の攻撃を防ぐ。前述のプリペアドステートメントがSQL向けの構造的な対策であるのに対し、エスケープ処理はHTML出力など様々な文脈で広く使われる、より汎用的な対策手法といえる。

## WAF(Web Application Firewall)
Webアプリケーションへの通信内容を検査し、SQLインジェクションやXSSなどの攻撃パターンを検知・遮断する機器・サービス。通常のファイアウォールがIPアドレスやポート番号といったネットワーク層の情報で通信を制御するのに対し、WAFはHTTPリクエストの内容(パラメータの値など)まで見て、既知の攻撃パターンに合致する通信を検知・遮断する。アプリケーション自体の脆弱性を直接修正するものではないため、「修正までの時間を稼ぐ緩和策」という位置付けで使われることが多く、根本的な対策であるセキュアコーディングと併用することが推奨される。

## CSP(Content-Security-Policy)
ブラウザが読み込める外部リソース(スクリプト、スタイルシート、画像など)の範囲をサーバ側が明示的に指定するHTTPヘッダ。「このページで実行してよいJavaScriptは自分のドメインから配信されたものだけ」といったポリシーを指定しておくことで、仮に攻撃者がXSSによって悪意あるスクリプトタグを埋め込めたとしても、ブラウザがそのスクリプトの実行をポリシー違反として拒否するため、被害を軽減する効果がある。XSSを「発生させない」対策ではなく「発生しても被害を抑える」多層防御の一環として位置付けられる。

## Cookieの属性(Secure/HttpOnly/SameSite)
Cookieに付与できる安全性を高めるための属性群。Secure属性を付けると暗号化されたHTTPS通信時のみCookieが送信されるようになり、平文のHTTP通信での盗聴を防ぐ。HttpOnly属性を付けるとJavaScriptからそのCookieにアクセスできなくなるため、XSSが発生してもセッションIDなどをスクリプト経由で盗まれるリスクを下げられる。SameSite属性は他サイトからのリクエストに対してCookieを送信するかどうかを制御するもので、CSRF対策としても効果を持つ。

## セッション管理
ログイン状態などを維持するための仕組み全般。HTTPはそれ自体では「状態を持たない(ステートレス)」プロトコルのため、ログイン後も「このリクエストは誰からのものか」を識別するためにセッションIDを発行し、以降のリクエストでそのIDを提示してもらう形で状態を維持する。セッションIDの発行方法(推測困難な十分にランダムな値であること)、保存方法、有効期限、ログアウト時の無効化処理などの設計が不十分だと、セッションハイジャックやセッションフィクセーション攻撃のリスクが生じる。

## セッションフィクセーション攻撃
攻撃者が事前に用意したセッションIDを被害者に強制的に使わせ、被害者がそのセッションIDでログインした後に、攻撃者が同じセッションIDを使ってログイン状態を乗っ取る攻撃。通常のセッションハイジャックが「既にログイン中の他人のセッションIDを盗む」のに対し、この攻撃は「攻撃者が決めたセッションIDを先に被害者に押し付けておく」という逆のアプローチを取る点が特徴で、対策としては、ログインが成功した時点で新しいセッションIDを再発行する(ログイン前のIDを無効化する)実装が基本となる。

## CSRF対策トークン
フォーム送信時に、推測困難なランダムなトークンを埋め込んでおき、送信されたリクエストにそのトークンが正しく含まれているかを検証することで、正規の画面を経由して送信されたリクエストであることを確認する対策。攻撃者が用意した悪意あるページから偽のリクエストを送らせようとしても、そのトークンの値を攻撃者は知ることができないため、サーバ側で不一致を検出してリクエストを拒否できる。前述のSameSite属性付きCookieと組み合わせることで、より強固なCSRF対策になる。
**前提条件**: CSRF攻撃そのものが成立するには、被害者が狙われているサイトに既にログイン済みで、有効なセッションを保持している状態でなければならない。ログアウトしている利用者に対してはCSRFは成立しない。

## クリックジャッキング / X-Frame-Options
透明あるいは視認しづらいiframeを正規のページの上に重ねて表示し、利用者に意図しないクリックをさせる攻撃。利用者は見た目上は無害なボタンをクリックしているつもりでも、実際には透明に重ねられた別サイトの「購入確定」ボタンなどをクリックしてしまっている、という形で意図しない操作をさせられる。X-Frame-OptionsヘッダをWebページのレスポンスに付与することで、そのページが他サイトのiframe内に埋め込まれること自体を禁止し、この攻撃を防ぐことができる(より新しいCSPのframe-ancestorsディレクティブで同様の制御を行うことも増えている)。

## HSTS(HTTP Strict Transport Security)
ブラウザに対し、今後は必ずHTTPSで接続するよう指示するHTTPヘッダ。一度HSTSが有効なサイトにHTTPSでアクセスすると、ブラウザはその情報を記憶し、以降は利用者が誤ってHTTPのURLを入力したりリンクをクリックしたりしても、通信を送る前に自動的にHTTPSへ変換してアクセスする。これにより、HTTPでの最初の接続を攻撃者に横取りされてHTTPのまま通信させられてしまう「SSLストリッピング」のようなダウングレード攻撃を防ぐ効果がある。

## オープンリダイレクト
外部から指定されたURLへそのまま転送してしまう実装の不備。「ログイン後に元のページへ戻る」といった機能で、戻り先のURLをパラメータとして受け取りそのまま使っている場合、攻撃者がそのパラメータに悪意あるフィッシングサイトのURLを指定したリンクを作成すれば、見た目は正規サイトのドメインなのに最終的に偽サイトへ転送されてしまう。利用者は信頼しているドメインのリンクだと思ってクリックしてしまうため、フィッシングの踏み台として悪用されやすい。

## DOM Based XSS
サーバを経由せず、ブラウザ内のJavaScriptがDOM(ページの構造を表すオブジェクト)を操作する過程で発生するクロスサイトスクリプティング。URLのフラグメント(`#`以降の部分、サーバには送信されない)の値をJavaScriptが読み取ってページに書き込む処理などに問題があると、サーバ側のログやレスポンス内容には何の異常も見られないにもかかわらず、ブラウザ内での処理だけでXSSが発生してしまう。サーバ側の対策(出力時のエスケープ処理など)だけでは防げないため、クライアント側のJavaScriptの実装にも注意が必要になる。

## HTTPヘッダインジェクション / HTTPレスポンス分割
改行コードなどを注入し、意図しないHTTPヘッダを追加・改ざんする攻撃。アプリケーションがユーザー入力をそのままレスポンスヘッダ(リダイレクト先のURLなど)に組み込んでいる場合、入力値に改行コードを混入させることで、本来1つのヘッダのはずの行を複数に分割させ、Cookieの不正な設定や、レスポンスの本文自体を書き換えるHTTPレスポンス分割につながることがある。入力値に改行コードなどの制御文字を許可しないよう検証することが対策の基本となる。

## JWT(JSON Web Token)
JSON形式のデータに署名を付与して、改ざん検知可能な形でやり取りするトークン形式。ヘッダ・ペイロード(ユーザーIDや権限などの情報)・署名の3つの部分がピリオドで連結された構造を持ち、サーバはこの署名を検証することで、トークンの内容が発行後に改ざんされていないことを確認できる。サーバ側でセッション情報を保持する必要がない(ステートレスな)API認証の仕組みとして広く使われているが、トークン自体に有効期限や失効の仕組みを適切に組み込んでおく必要がある。

## OAuth 2.0
ユーザーがパスワードを渡さずに、第三者アプリへ限定的なアクセス権限を許可するための認可(Authorization)フレームワーク。例えば外部サービスに「自分のGoogleカレンダーの予定を読み取る権限だけ」を渡したい場合、ユーザーはGoogleの画面上で許可を与えるだけで、自分のGoogleパスワードを外部サービスに直接教えることなく、発行されたアクセストークンを通じて限定的な権限だけを委譲できる。「認証(本人確認)」ではなく「認可(権限の委譲)」のための仕組みである点が、よく混同されるポイントとして注意が必要。

## CORS(Cross-Origin Resource Sharing)
異なるオリジン(ドメイン・ポート・プロトコルの組み合わせ)間でのリソース共有を、サーバが明示的に許可するための仕組み。ブラウザは標準で「同一オリジンポリシー」に基づき、異なるオリジンへのJavaScriptからのリクエストを制限しているが、正当な理由で他のドメインのAPIを呼び出したい場合、サーバ側がレスポンスヘッダで「このオリジンからのアクセスを許可する」と明示することで、ブラウザがそのクロスオリジン通信を許可するようになる。設定を誤って過度に広く許可してしまうと、意図しないサイトからのデータ読み取りを許してしまうリスクがある。

## 脆弱性診断(ペネトレーションテスト)
実際に攻撃を模した手法でシステムに侵入を試み、脆弱性の有無や影響範囲を検証するテスト。自動化されたツールによる既知の脆弱性パターンの網羅的なスキャン(脆弱性診断)と、人間の診断者が実際の攻撃者のように手動で侵入を試み、発見した脆弱性を連鎖させて実際にどこまで被害が及ぶかを検証するペネトレーションテストは、厳密には異なる位置付けで語られることもある。どちらもシステムを公開する前や定期的なタイミングで実施し、実際の攻撃を受ける前に弱点を発見・修正することを目的とする。

## ファジング
通常想定されない大量・異常な入力データ(フォーマット外の値、極端に長い文字列、ランダムなバイナリなど)を自動的に生成して与え、プログラムの異常動作やクラッシュを検出するテスト手法。人間が想定しきれないようなエッジケースの入力パターンを機械的に大量に試すことで、バッファオーバーフローのような実装上の不具合に起因する脆弱性を効率的に発見できる。OSSのプロジェクトやブラウザなど大規模なソフトウェアの脆弱性診断で広く活用されている。

## SAST / DAST
SAST(Static Application Security Testing、静的解析)はソースコードやバイナリを実際に実行せずに解析して脆弱性を検出する手法で、開発の早い段階(コードを書いた直後)から適用できる利点がある。DAST(Dynamic Application Security Testing、動的解析)は実際にアプリケーションを動作させ、外部から実際のリクエストを送ることで脆弱性を検出する手法で、実際の実行環境に近い条件での検証ができる。両者は検出できる脆弱性の種類や段階が異なるため、CI/CDパイプラインに組み込んで両方を併用することが望ましいとされる。

## OWASP Top 10
Webアプリケーションにおける代表的なセキュリティリスクを、国際的な非営利団体OWASP(Open Worldwide Application Security Project)がまとめたランキング。数年おきに実際の脆弱性報告の統計などを基に更新され、アクセス制御の不備やインジェクション、セキュリティの設定ミスといった項目が継続的に上位にランクインしている。Web開発者やセキュリティ診断の担当者が「最低限押さえるべきリスクの一覧」として、業界で広く参照される事実上の標準になっている。

## ホワイトリスト方式 / ブラックリスト方式
ホワイトリスト方式は許可するものだけを列挙し、それ以外はすべて拒否する方式。ブラックリスト方式は禁止するものだけを列挙し、それ以外はすべて許可する方式。例えば入力値検証において「使ってよい文字種だけを列挙する」のがホワイトリスト方式、「危険な文字列のパターンだけを拒否する」のがブラックリスト方式に相当し、攻撃者は新しい回避パターンを次々と考え出すため、未知の攻撃手法にも対応できるホワイトリスト方式の方が、一般的に安全性が高いとされる。

## リクエストスマグリング
フロントエンド(ロードバランサやリバースプロキシ)とバックエンド(実際のアプリケーションサーバ)がHTTPリクエストのヘッダ(Content-LengthやTransfer-Encodingなど)を異なる方法で解釈してしまうことを利用し、1つのリクエストの中に別のリクエストを「密輸(スマグリング)」して処理させる攻撃。前段と後段のサーバの実装の間に生じる解釈のズレを突くため発見が難しく、成功するとキャッシュの汚染や、他の利用者のリクエストへの不正な混入といった深刻な影響を及ぼすことがある。

## APIセキュリティ
Web APIの認証・認可・入力検証・レート制限など、API特有のセキュリティ対策全般を指す概念。従来のWebアプリケーションが人間のブラウザ操作を前提に設計されるのに対し、APIはプログラム同士の直接的なやり取りを前提とするため、過剰な数のデータを一度に返してしまう設計の不備(過剰なデータ露出)や、アクセス制御の抜け(他人のIDを指定すれば他人のデータが見えてしまうBOLA/IDOR)など、API特有のリスクが存在する。OWASPもWebアプリケーションとは別にAPI向けのTop 10を公開している。

## バインド機構
SQL文の構造とデータを分離して実行する仕組み。SQL文のテンプレート(構造)をあらかじめデータベースエンジンに送って解析・コンパイルさせておき、その後にパラメータの「値」だけを個別に送って実行するという2段階の処理を行うことで、値の中にSQLの制御文字が含まれていてもテンプレートの構造自体が変化しないようにする。この仕組みをプログラミング言語側から利用しやすい形で提供したものが、前述のプリペアドステートメントということになる。
